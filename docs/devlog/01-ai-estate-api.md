# Devlog 01. 디지털 유산 분석 API 구현

## 작업 배경

기존 BlockWill은 다음과 같은 구조를 가지고 있었다.

```text
유언 파일 작성
→ 브라우저에서 AES 암호화
→ Express API를 통해 SQLite에 저장
→ 스마트 컨트랙트에 유언 정보와 자산 예치
→ 주기적인 생존 신고
→ 비활동 기간 경과 후 상속자 수령

초기 버전은 블록체인 기반 상속 흐름을 실험할 수 있었지만, 사용자가 가진 여러 디지털 자산과 상속 의도를 구조적으로 관리하기 어려웠다.
예를 들어 사용자가 다음과 같이 작성했을 때:
ETH는 동생에게 주고 싶다.
BTC는 부모님에게 전달하고 싶다.
Google Drive의 가족사진도 부모님에게 전달하고 싶다.
기존 시스템에서는 이 내용을 그대로 암호화해 저장할 뿐, 어떤 자산이 존재하고 누구에게 전달하려는 것인지 분석할 수 없었다.
이를 개선하기 위해 첫 번째 확장 기능으로 디지털 유산 분석 API를 구현했다.
개발 환경 구성
기존 백엔드는 Node.js와 Express로 작성되어 있다. AI 분석 기능은 데이터 검증과 Structured Output 처리가 편리한 Python과 FastAPI로 분리했다.
현재 백엔드 구조는 다음과 같다.
backend/
├── server.js
├── package.json
├── app/
│   ├── main.py
│   ├── models.py
│   ├── estate.py
│   └── security.py
├── tests/
│   └── test_api.py
└── requirements-lock.txt
기존 Express 서버는 암호화된 유언 데이터 저장 기능을 담당한다. FastAPI 서버는 디지털 유산 분석과 복구 정책 검증을 담당한다.
두 서버의 역할을 한 번에 변경하지 않고, 기존 기능을 유지한 상태에서 분석 기능을 별도로 추가했다.
가상환경 설정 중 발생한 문제
처음 Python 가상환경을 생성하는 도중 명령을 중단하면서 .venv 폴더가 불완전하게 만들어졌다.
KeyboardInterrupt
이 상태에서는 Python 실행 파일은 존재했지만 pip와 activate 파일이 만들어지지 않았다.
다음과 같이 가상환경 구성을 나눠서 완료했다.
/opt/homebrew/bin/python3.11 -m venv --without-pip .venv
.venv/bin/python -m ensurepip --upgrade -v
.venv/bin/python -m pip install -r backend/requirements-lock.txt
이 과정에서 가상환경 생성 명령이 끝나기 전에 중단하면 일부 파일만 생성될 수 있다는 것을 확인했다.
디지털 유산 분석
POST /api/estate/analyze는 여러 문서 조각을 입력받아 디지털 자산 정보를 구조화한다.
입력 예시:
{
  "documents": [
    {
      "id": "memo-a",
      "text": "Sepolia ETH는 동생에게 주고 싶다.\nUSDC가 있다."
    },
    {
      "id": "memo-b",
      "text": "Sepolia ETH는 부모님에게 전달한다."
    }
  ]
}
분석 결과에는 다음 내용이 포함된다.
- 자산명
- 자산 분류
- 네트워크
- 지갑 주소
- 상속 대상 후보
- 누락 정보
- 충돌 여부
- 원문 근거
- 현재 시스템에서 실행 가능한지 여부
위 예시에서는 ETH의 상속 대상이 문서마다 다르기 때문에 충돌로 표시된다. USDC에는 상속 대상이 없으므로 누락 정보가 생성된다.
시스템이 임의로 한 명을 선택하지 않고 사용자가 직접 결정하도록 구성했다.
On-chain 자산 분류
모든 디지털 자산을 스마트 컨트랙트로 이전할 수 있는 것은 아니다.
현재 MVP에서는 다음 조건을 충족한 ETH만 복구 정책 후보로 분류한다.
자산 = ETH
보관 유형 = 개인 지갑
네트워크 = Sepolia
거래소 자산과 Google Drive 같은 외부 계정은 EXTERNAL_OR_UNSUPPORTED로 표시한다.
AI가 실행 가능하다고 판단하더라도 백엔드 규칙을 통과하지 못하면 On-chain 대상으로 분류되지 않는다.
민감정보 보호
문서를 LLM에 전달하기 전에 민감정보를 검사하도록 구현했다.
현재 차단하는 대표 입력:
- Private Key
- Seed Phrase
- Recovery Phrase
- API Secret
- Password
- 64자리 개인키 후보
- OpenAI API Key 형태
- 영문 BIP-39 단어가 연속된 복구 문구 후보
이메일, 전화번호, 주민등록번호 형태의 정보는 제거 표시로 대체한다.
민감정보가 발견되면 일부만 제거한 뒤 분석을 계속하지 않고 요청 전체를 거부한다. 복구 문구가 외부 분석 API에 전달될 가능성을 줄이기 위한 결정이다.
문서 본문뿐 아니라 문서 ID도 외부 분석에 포함되므로 동일한 검사를 적용했다.
Zero-Trust 출력 검증
분석 결과는 그대로 사용하지 않고 원문과 비교한다.
다음 경우 분석 결과를 거부한다.
- 존재하지 않는 문서 ID를 반환한 경우
- 원문에 없는 증거 문장을 반환한 경우
- 원문에 없는 지갑 주소를 반환한 경우
- 원문에 없는 상속 대상을 반환한 경우
- 원문에 없는 네트워크를 반환한 경우
- 잘못된 형식의 지갑 주소를 반환한 경우
이 검사는 LLM의 결과가 JSON 형식을 만족한다는 것만으로 충분하지 않다는 판단에서 추가했다.
복구 정책 검증
분석 결과를 바로 스마트 컨트랙트에 전달하지 않고 별도의 정책 검증 단계를 추가했다.
현재 안전 기준:
비활동 기간: 최소 90일
복구 유예기간: 최소 7일
Guardian: 3명
필요 승인: 2명
소유자, 상속자, Guardian 주소는 모두 서로 달라야 한다.
위험한 정책은 HIGH로 반환하고 확인 API에서도 거부한다.
정책 확인 API가 성공하더라도 트랜잭션은 발생하지 않는다. 최종 실행은 추후 프론트엔드에서 사용자가 지갑으로 서명해야 한다.
테스트
다음 명령으로 테스트를 실행했다.
bash scripts/test-api.sh
결과:
37 passed
테스트에서는 정상 입력뿐 아니라 민감정보, 잘못된 주소, 중복 Guardian, 위험한 기간, 조작된 분석 결과 등을 함께 확인했다.
현재 상태
이번 단계에서 완성한 흐름은 다음과 같다.
사용자 텍스트
→ 민감정보 검사
→ 자산과 상속 대상 추출
→ 원문 근거 검증
→ 누락 및 충돌 표시
→ 복구 정책 검증
→ 사용자 확인 대기
현재 demo 모드는 규칙 기반으로 동작한다. OpenAI Structured Outputs를 사용하는 코드도 작성했지만 실제 API 계정 호출은 아직 검증하지 않았다.
다음 개발에서는 기존 claim() 방식의 스마트 컨트랙트를 바로 교체하지 않고, Guardian 승인과 복구 유예기간이 포함된 새로운 Recovery Contract를 별도 파일로 추가할 예정이다.
